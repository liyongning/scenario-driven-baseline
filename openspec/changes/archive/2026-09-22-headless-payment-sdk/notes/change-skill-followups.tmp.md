## 后续要处理的内容

- 场景稳定 ID：把当前依赖项目 AGENTS/测试规范的约定沉淀到 Change 工作流。规划时检查每个 Scenario 的稳定唯一标识，生命周期中的增改删/迁移保持身份；覆盖报告不能从现有测试反推分母。具体命名可由项目配置，不能把 TC-PAYSDK 前缀硬编码进通用 Skill。
- 先验证可行性：提出门禁时先核实现有 Schema/Spec/代码是否具备对应字段、标识、CLI 和证据，明确已实现、规划新增、仍未知；禁止把设计目标说成现成功能。
- 测试粒度：Scenario 与 case 多对多；关键跨模块交互需要连续流程测试。单项行为全部通过不能替代组合流程贯通；怎样抽取最小必需流程、约束关联数据/阶段连续性，应结合 SDK 实践再形成通用方法。
- 测试事实与数据分离：Spec 提供行为与预期，IDL 提供协议；测试代码实现步骤/断言，Fixture 提供输入/模拟响应。testing 工具目录、用例代码、数据和报告各有职责，避免把 Fixture 当成完整测试 DSL。
- 执行证据：事实清单、具体 case/检查点绑定与本次报告交叉验证，记录环境及输入摘要；缺失、skip、draft、失败、旧报告和空断言不能宣称完成。语义是否正确仍须评审，不能声称 ID 或断言计数证明测试有效。
- 方案阶段的实施保障：完整技术选型、包内目录、依赖方向、根/包 AGENTS 正文、初始化命令、官方来源、必要配置差异、统一验证入口与任务责任应在设计中闭合，不能只在 Task 写“搭建工程”。
- 官方与社区能力优先：脚手架存在则锁版使用；没有完整脚手架则引用官方最小配置/成熟工具，只实现项目专属连接和规则。记录模板版本、命令、配置差异与实际验证；不凭空假设某工具有一键初始化能力。
- AGENTS 与机器门禁协作：说明规则在哪里、谁执行、哪些可机械验证、哪些需语义评审。仅创建 AGENTS/CI 文件不算强约束生效，必须有违规反例和实际运行/保护配置证据。
- 阶段与状态一致：方案文件存在、静态 validate 通过、脚手架跑通、测试通过、真实渠道验收分别报告；禁止越级宣称完成。项目未决契约不由实施 Agent 补义。
- 逐任务验收：方案阶段为任务声明交付物、验证命令、明确通过条件和原始证据；TDD 不替代退出门禁。质量基建需验证真实工具的正向与反例，测试基建还要贯通事实输入、用例设计、版本化测试/Fixture、执行和报告；区分工具演练、单任务完成、工程交付、真实环境验收及实际发布。早期任务不伪造未来全量通过，正式 Verification 只在对应阶段生成。
- 可配置而非照搬：手写覆盖率 100%、三包布局、微信平台与当前选型是本项目要求；通用 Skill 应要求声明并落实项目阈值/边界，不把这些具体值强制推广到全部项目。
