## 用户带回的服务端协作结论

- 登录态失效影响渠道支付签名、需要恢复支付时，重新下支付单。由此产生的冗余无效支付单一期保留，二期由服务端自动关单。
- 用户补充明确：已经完成支付的交易不能重新下单；查询等业务鉴权场景换用新的业务登录态即可。业务 Access Token 与渠道会话/签名问题需要分开处理。
- 据此关闭 SDK-P01 的恢复策略选择与 SDK-P04 的旧支付单复用/重签策略选择；剩余设计待决项是 SDK-P02（支付参数及响应契约）。

## 本次 SDK 草案细化

- 复用现有 pay/query/observe：准备鉴权失败后由业务恢复 Token，再显式 pay 原交易；结果查询中断后仅 query/observe 原交易；渠道会话明确失效后，由业务完成服务端会话更新，再显式 pay 获取新支付单与签名。
- SDK 接口细化：原 Promise 在中断时结束；PaymentOutcome 增加 interruptedPhase，避免业务猜测恢复入口。此字段名称及具体 TypeScript 类型属于 SDK 的待评审接口草案，不声称由服务端定义。
- 本地清理细化：使用既有 RunOptions.cancellation 明确 invoke 等待的停止、订阅清理及旧回调隔离，补入 ChannelContext 和本地 stopped 返回；不新增渠道回调计时器、登录控制器或渠道 abort。
- 同步 Proposal、两份 Spec、Design 编号时序、Task 3/4/5/8 的契约及验收要求、FLOW-006 连续调用断言和根 Agent 入口。所有测试仍为 draft，八个任务未勾选。
