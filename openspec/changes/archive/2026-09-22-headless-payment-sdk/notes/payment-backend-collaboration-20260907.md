阳阳，我们在设计通用支付 SDK，首期接入微信小程序虚拟商品支付。前端方案准备进入 Plan Review／实施，目前有 3 项需要和支付基建服务端共同确定的契约。下面把背景、场景和需要确认的结果整理一下，方便直接讨论。

**链路背景与职责**

1. 业务后端先创建交易，业务前端拿到 trade_no。
2. 业务前端调用 SDK 的 pay，传入已有交易号和支付方式。
3. SDK 调支付基建 CreateTradePay 预下单，取得支付单标识及 pay_params。
4. SDK 消费支付参数，调用 wx.requestVirtualPayment 拉起渠道收银台。
5. 收到渠道成功提示或已返回的未知结果后，SDK 调 QueryTrade 确认交易事实；明确取消／调起失败按已确认映射返回业务。渠道回调本身不等于服务端 PAID。

SDK 自带网络能力，按支付契约组装请求，每次请求读取业务提供的当前 Access Token；业务负责登录恢复，SDK 不自动登录、刷新凭据或重放预下单。微信身份和虚拟支付 session_key 由服务端维护，SDK 不接收 OpenID、session_key 或签名密钥。SDK 不维护订单支付历史，也不根据前端计时推导关单。

以下是待共同决策的问题，恢复接口和流程没有由前端单方面定案。当前核对基线为 2026-09-06 的 IDL 285f1be60fb218c5f34908faa8ca6b033963cd65，以及支付基建技术方案 revision 406；如果已有更新，请直接提供最新契约／文档，我们按新版对齐。

**1. SDK-P01：中途身份／会话失效后，原支付流程如何续接**

需要覆盖这几种具体情况：

- 场景 A：业务 CreateTrade 已成功，trade_no 已交给 SDK；SDK 请求 CreateTradePay 时 Access Token 失效。业务静默登录更新 Token 后，如何继续这笔已存在的交易？
- 场景 B：请求已经通过网关，但服务端内部 RPC 后续失败。需要区分实际可能发生的鉴权／身份／渠道会话错误；此时是否已创建 payment_no、生成渠道订单或发生外部调用，前端不能仅凭“鉴权错误”推断交易没有推进。
- 场景 C：CreateTradePay 已成功并返回参数，但调用虚拟支付 API 时收到渠道会话失效；或者渠道动作已经发生，后续 QueryTrade 才发现 Access Token 失效。凭据恢复后，前者是否需要重新获取签名参数，后者是否应从查询继续？各自安全的恢复步骤是什么？
- 场景 D：小程序／微信异常退出后重新进入，或业务交互已经结束但进程还在、一直没收到渠道回调。SDK 不设收银台等待时限；业务与 SDK 需要明确本地调用何时结束、旧回调如何隔离，以及重新进入后如何查询／继续原交易。这里的本地 Promise 和清理方式由前端设计，服务端需配合明确可查询的交易事实与再次请求语义。

请一起明确：

1. 业务鉴权失效、微信身份未绑定、虚拟支付会话失效分别由哪个环节识别、返回哪些稳定错误码／字段？内部 RPC 的错误怎样透传到 HTTP 契约？哪些情况下可能已有支付副作用，需要保留哪些交易／支付单标识？
2. Access Token 与渠道会话分别由谁、通过什么接口恢复？服务端能自行续期哪些信息，哪些必须由业务端重新登录配合，怎样判定恢复完成？还需要考虑恢复后账号变化的情况。
3. 每个中断位置恢复后应执行哪一步：查询原交易、重新获取支付参数，还是调用其他明确接口？什么时候允许再次调渠道，什么时候必须先查交易？
4. 共同确定 SDK 的中断结果、恢复入口及所需上下文；原 pay 是结束后显式恢复，还是保留等待，需要结合上述服务端能力选定，不能留给实施时猜。

希望产出：带步骤编号的时序图，以及“失败位置 → 错误码 → 是否已产生副作用 → 保留的标识 → 凭据恢复方／接口 → 下一步”的矩阵，并明确所需 IDL／补充契约变化。SDK API 和本地生命周期由前端配合补齐。

**2. SDK-P02：pay_params 精确结构，以及响应判错优先级**

目前 IDL 的 CreateTradePayResponse.pay_params 是 string，字段类型本身不足以说明字符串内部的渠道参数结构。我们核对的技术方案 §9.11.3 将 mode=short_series_goods 列在 signData 内容里；微信官方调用示例中，mode 与 signData、paySig、signature 位于调用参数顶层。

这是已核对版本的文档描述差异，我们尚未取得服务端实际支付响应，不能据此断言实现有问题。如果服务端有自己的封装，也可以，只需明确到渠道 API 的映射。

请提供／确认：

- 首期虚拟支付 pay_params 的准确 JSON 结构、字段类型／必填性、枚举及版本规则；特别是 mode、signData、paySig、signature 的位置。其他渠道未来接入时再冻结各自结构。
- 与当前实现一致的完整 HTTP／ProtoJSON 响应样例，以及用于结构与错误分支验证的脱敏 Fixture；说明 pay_params 外层字符串的编码方式和 signData 原始字符串如何保留。SDK 会校验外层并透传签名原文，不解析后重序列化签名内容，也不在前端补签。
- HTTP 状态与 BaseResp.success、status_code、error 的判错优先级；例如 success=true 但同时存在错误码／error、部分字段缺失或响应不完整，应怎样处理？请给正常、失败、冲突／缺失报文及期望结果，避免 SDK 把歧义响应当成可支付参数。

**3. SDK-P04：同一交易再次请求时，复用／重签如何保证参数仍可用**

具体场景：交易 T 第一次 CreateTradePay 取得支付单 P 和签名参数，随后发生会话失效；业务／服务端恢复了渠道会话，再用同一 trade_no、同一 channel 请求 CreateTradePay。如果幂等逻辑复用了原支付单，返回的是原参数，还是基于新会话重新签名的有效参数？哪些情况下需要新的 payment_no 或渠道 outTradeNo？

另一类情况是用户取消后显式再次付款，或者渠道结果未知／交易已经支付时又请求同一交易。SDK 会把它作为一次新的显式调用，由服务端裁决，不能自行认定一定要创建新支付单或一定可以复用旧参数。

请明确：

1. 同 trade_no／channel 的幂等键、支付单复用条件、参数刷新／重签条件和失效参数处理方式。
2. session_key 更新后签名如何更新，payment_no 与渠道 outTradeNo 分别保持还是更换，如何满足渠道订单号的使用约束？
3. 对未支付、已调起但结果未知、明确取消、已支付、过期／已关闭等实际支持状态，再次 CreateTradePay 分别返回什么；并发或重复请求怎样裁决？请区分当前一期行为和后续能力。

希望产出：“交易／支付单状态 + 会话是否变化 + 再次请求 → 复用或新建 → 是否重签 → 返回标识／参数／错误”的矩阵，并与 P01 的恢复动作、P02 的响应结构一致。

自动关单及服务端与渠道期限协调按服务端规划推进，不作为本项关闭条件，也不要求前端增加收银台计时器。

这 3 项分别解决“从哪里继续”“拿到什么参数／错误”“参数如何复用或更新”，需要一起串通。若已有契约覆盖，直接指明最新文档／IDL／样例即可；有缺口的部分我们再共同定下来。结论会写回 SDK 的 Spec、Design、Tasks 和测试预期，然后进入独立方案评审与实施。
