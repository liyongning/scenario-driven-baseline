# 模板使用指南

本指南是使用方（含 Agent）基于本模板演进的入口。工程形态的唯一事实来源是根目录 [project.manifest.json](../project.manifest.json)（[schema](../project.manifest.schema.json)）：改包、命令、测试项目或发布设置时先改清单，再改代码。三级 `AGENTS.md` 与每个 AGENTS.md 旁的 `CLAUDE.md` 给出分层的硬约束，结构由 `pnpm check:project-map` 核对；本指南给出能力清单、推进流程、替换点地图与复刻验收方法；[技术架构文档](architecture.md) 回答"解决什么问题、为什么这样设计"。

## 从方案到验收

模板把"规划 → 评审 → 实现 → 验收 → 归档"固化成一条链，每一步都有可运行的门禁与证据。

1. **OpenSpec 规划**：用 `/change plan <change>` 在 `openspec/changes/<change>/` 下写 proposal、specs、design、tasks。需求与场景先进 Spec；每个 Scenario 带 `json verification` 元数据，FLOW 行必须符合格式 schema。
2. **Plan Review**：`/change plan-review <change>` 冻结规划 digest 并派发独立评审；digest 变化即作废本轮结论。未通过不得实施。
3. **实现**：`/change apply <change> --commit` 在独立 worktree 中按 Task 实施；Task 结束时运行 `pnpm test:affected`，交回前运行 `pnpm verify`。每个 Task 的验收记录写入该 Change 的 verify 记录（`openspec/changes/<change>/verify.md`）；`artifacts/` 只是本地运行产物目录，不是验收结论的载体。
4. **运行约定（有 active Change 时）**：仓库存在正在交付的 active Change 时，任何可能触发副本用例的运行都要带作用域——全量运行用 `pnpm verify --change <change>`，单独运行 `check:fast` 或 `test:affected` 时设置 `SCENARIO_GATE_CHANGES=<change>`。副本据此归档对应 Change；没有 active Change 时不带作用域，副本也无需归档。这条约定同样适用于复刻验收的演练副本。
5. **快速门禁**：`VERIFY_RUN_ID=<run-id> pnpm check:fast`。它依次运行 `pnpm proto:validate`、`pnpm proto:status`、`pnpm format:check`、`pnpm lint`、`pnpm build`、`pnpm typecheck`、`pnpm check:architecture`、`pnpm test:unit`、`pnpm check:coverage`、`pnpm check:fixtures`、`pnpm test:integration` 与 `pnpm check:package`，手写代码四项覆盖率要求 100%。
6. **按需运行**：`pnpm test:affected [--base <ref>] [--scenario <ID...>] [--dry-run]` 只跑受改动的 Spec、Fixture、代码与门禁模块影响的用例；改动命中清单、构建输入或工具配置时退化为全量 `pnpm check:fast` 并打印原因。按需运行的报告带 `partial` 标记，场景门禁会拒收，所以它不能替代全量证据。节奏：每个任务结束时按需运行，至少每 3 个任务与交回前、验收前全量运行。
7. **平台用例**：按 [packages/e2e/AGENTS.md](../packages/e2e/AGENTS.md) 的约定逐文件运行小程序用例，每个文件前退出开发者工具主进程并预热约 25 秒（`pnpm weapp:prepare` 会轮询到能读到版本号为止，就绪与否以该命令的退出码为准，不依赖固定等待）；每个文件一份报告，失败时整文件重跑。整次 `pnpm verify` 在平台步骤中断（例如开发者工具掉线、某个文件超时）时，按它打印的提示用 `pnpm verify --from test:e2e:<项目名> --run-id <run-id>` 续跑：跳过此前已通过的步骤、沿用同一 run id 重新生成该步及之后的报告，补齐平台与门禁证据，不必从头再跑。
8. **场景门禁**：`VERIFY_RUN_ID=<run-id> pnpm check:scenarios`，用 unit、integration 与全部 weapp 报告对账 Spec、绑定与证据；退出码 0 且问题数为 0 才算通过。默认读取 `artifacts/<run-id>/reports/`，也可用 `--report` 逐个指定报告。
9. **归档**：`/change archive <change>`。归档前确认清单、绑定、报告与来源摘要仍然一致。
10. **用例落位与覆盖率排除**：integration 用例放在 `packages/e2e/tests/{protocol,tooling,flows,sdk}/**/*.spec.ts`（示例用例另在 `packages/e2e/tests/example/**`），weapp 用例放在 `packages/e2e/tests/weapp/**/*.spec.ts`；两组目录来自 [packages/e2e/vitest.config.integration.ts](../packages/e2e/vitest.config.integration.ts) 与 [packages/e2e/vitest.config.weapp.ts](../packages/e2e/vitest.config.weapp.ts) 的 `include`，新用例落在其中就会被对应项目执行，不要另建测试项目。新增 weapp 宿主 runner（`packages/e2e/host/weapp/` 下的文件）时，它只在微信开发者工具里执行、不计入手写代码覆盖率：要在 [project.manifest.json](../project.manifest.json) 的 `quality.coverageExclusions` 里登记该文件与理由，`pnpm check:coverage` 按清单核对，不要改门禁脚本。

证据位置：报告与覆盖率都在 `artifacts/<run-id>/`（`reports/`、`coverage/`）。`VERIFY_RUN_ID` 决定 `artifacts/<run-id>/reports/` 下各报告的文件名，生成报告与对账必须使用同一个 run-id；未设置时回退到 `local`。验收结论写在 Change 的 verify 记录里，不再写入 `artifacts/<run-id>/tasks/`。

## 初始化方式

1. **复制模板（不带历史）**：以本仓库内容为基线创建使用方仓库，不带原仓库的历史与远端。
2. **安装工作流**：安装 Change Skill 或等价的 `openspec-workflow` 工作流。工作流 schema 不随模板提交，需要在使用方安装；本模板只要求 OpenSpec 根与 4 条硬规则。
3. **适配评估**（项目形态不是 SDK，或协议来源、运行平台与模板不同时必做；例如 Web 应用、跨端应用、非 IDL 接口）：先读本指南与使用方自己的产品方案、技术方案，只出结论、不改代码。对"能力地图"的每一行与"替换点地图"的每一项给出结论：保留、替换、删除或新增；同时列出项目需要而模板没有的能力（例如应用骨架、路由、UI、浏览器端到端测试、部署）。技术选型在这一步一并确定。输出一张表（能力或替换点 / 结论 / 理由 / 涉及文件）加一份"模板缺失能力"清单，作为第一个 Change 规划的输入。
4. **仓库已有 OpenSpec 根与活跃 Change**：不要整体覆盖使用方的 `openspec/`。按需把模板的主 Spec 以 `ADDED` delta 引入到使用方自己的第一个 Change 中；存量 Scenario 还没有 `json verification` 元数据时，用 `SCENARIO_GATE_CHANGES` 与 `--change` 限定作用域分批补齐，再逐批用场景门禁验收，避免一次改动全部 Spec 让证据对不上。
5. **新建第一个 Change**：在使用方仓库里用一个 Change 完成改造（依据适配评估的结论）：
   - 改根 [project.manifest.json](../project.manifest.json)：包目录与包名（`manifest.packages[].directory`、`manifest.packages[].name`）、允许目录、必需命令、测试项目与摘要目录；发布能力仍在时还要改 `manifest.release` 的项（如 `tagPrefix`）。改名范围自定：只改产品包，或连 protocol/e2e 包一起改，改后都要让清单、锁文件与门禁一致。
   - 包名或目录改动后同步：各包 `package.json` 与 `publishConfig`、[pnpm-lock.yaml](../pnpm-lock.yaml)（跑一次 `pnpm install` 更新软链与锁文件）；根 [package.json](../package.json) 的 build 过滤与脚本；[tsconfig.base.json](../tsconfig.base.json)、[tsconfig.test.json](../tsconfig.test.json)、[vitest.config.ts](../vitest.config.ts)、[eslint.config.js](../eslint.config.js)、[.dependency-cruiser.cjs](../.dependency-cruiser.cjs) 中（包名与路径的 glob 已按清单派生：`.dependency-cruiser.cjs` 与 `eslint.config.js` 直接读 `project.manifest.json`，`vitest.config.ts` 的测试项目也由清单生成，改清单即可，不要手改其中的包名 glob）；以及 [AGENTS.md](../AGENTS.md)、[README.md](../README.md) 中作为示例出现的包路径。
   - 按"替换点地图"替换或删除可替换点：协议来源、运行平台、包发布。
   - 新增自己的业务模块：按工厂 → 核心 → 端口 → 适配器分层，业务目录之间不得互相导入，就近单测覆盖新代码以满足手写代码 100% 阈值。
   <!-- template-example:begin -->
   - 样板写法见示例模块 [packages/sdk/src/example](../packages/sdk/src/example) 与示例用例 [packages/e2e/tests/example](../packages/e2e/tests/example)；删除示例后本节不再适用。
   <!-- template-example:end -->
   - 分层守卫按目录模式自动覆盖 `src/` 下除 `runtime/` 外的全部业务模块，新增模块无需修改配置：[.dependency-cruiser.cjs](../.dependency-cruiser.cjs) 的 `domain-core-no-generated`（core/ports 不得导入 generated）、`core-no-platform-or-node`（不得依赖 Node 内置模块）、`domain-isolation`（业务模块互不导入），以及 [eslint.config.js](../eslint.config.js) 的 `no-restricted-globals: wx`。业务模块须使用 `core/`、`ports/` 目录名才受约束。需要对外时在 [packages/sdk/src/index.ts](../packages/sdk/src/index.ts) 导出。
6. **先加后删**：自己的业务覆盖到示例承担的能力后，再按下一节的删除白名单移除示例；删除时对应的 Scenario、FLOW、Fixture 与用例一并处理。
7. **验收**：用统一入口收尾——`pnpm verify`（没有 active Change 时按运行约定不带作用域），它按运行约定把快速门禁、逐文件 weapp 与场景门禁对账串成一次运行；需要单独补证据时再按"从方案到验收"逐项运行。

五条维护规则：

- 删除或替换"替换点地图"中的某一项后，对应的三级标题仍要保留，正文改写为"本项目已删除……"或"本项目已替换为……"，不要删掉标题本身。
- 指南中引用、但已随该项删除的 Scenario ID 必须同时删除，否则事实一致性检查会报"未登记的 Scenario ID"；能力地图中对应行的承载文件与验证方式也要同步。
- 删除代码常会让"手写代码 100% 覆盖"失去覆盖来源，`pnpm test:unit` 与 `pnpm check:coverage` 会失败；删除后同步处理受影响的单测与用例，不要靠豁免覆盖率。
- 仓库里还有未归档 Change 时，主 Spec 与它的 Spec delta 必须一致：删除主 Spec 的 Requirement 会让引用它的 `MODIFIED`/`REMOVED` delta 失效，`pnpm check:fast` 的 Spec 清单校验随之失败；先同步处理或先归档该 Change。
- 删除能力后同步更新 [README.md](../README.md) 与各 `AGENTS.md` 中声明该能力的句子，以及根 [package.json](../package.json)、[vitest.config.ts](../vitest.config.ts)、[.gitignore](../.gitignore) 等引用已删文件的工程配置。

**模板反馈日志**：使用方在使用方仓库的 `docs/template-feedback.md` 中持续记录使用模板时的发现，每条写明位置、现象、处理方式与类别：1 阻塞（不越过指南边界就无法完成，或门禁不稳定）、2 指引错误或误导（照字面执行会出错）、3 需要额外理解（指南未逐项列出，靠 `git grep`、读代码或门禁报错补全）、4 模板缺失能力（项目需要、模板没有）。第 1、2、4 类由模板维护者汇总回本模板，以新的 Change 迭代；第 3 类不要求修复。

**扩展更多包**：清单 schema 与读取方当前认定 product、protocol、test 三种角色各一个包；角色、包数量与允许目录由 [project.manifest.schema.json](../project.manifest.schema.json) 与 [scripts/lib/project-manifest.ts](../scripts/lib/project-manifest.ts) 共同约束，扩展时同步修改两处与对应门禁。

**已知限制**：小程序自动化仍不稳定，开发者工具在同一主进程上重复 `launch` 可能挂起，预热约 25 秒只能消除冷启动超时（`weapp:prepare` 的就绪探测读不到版本号会直接失败，不再让首个 case 随机超时）；平台能力替身目前只有文字标准（[packages/e2e/src/drivers](../packages/e2e/src/drivers)），没有代码样例：替身按产品包里定义端口的适配器实现，放在 `packages/e2e/src/drivers/`，由用例在调用宿主 runner 前注入，宿主 runner 只按消费接口声明发真实 `wx.request` 并把原始结果交回用例，所以替换平台能力时改驱动与用例注入，不改宿主 runner 与断言；替换点地图列出主要接缝，完整影响范围以 `git grep` 与门禁报错为准（例如写死旧包名的测试、平台删除后失去覆盖来源的单测、依赖清单内容的单测），照着改即可；替换点地图只经过模拟演练，尚未在真实使用方验证，真实使用中的发现请记入上面的模板反馈日志。

## 移除模板示例

初始化阶段（模板示例仍未被使用方自己的业务替换时）可以整块移除示例，不必为它写 Change、`REMOVED` delta 或走归档。**时机**：使用方自己的第一个 Scenario 通过完整门禁之后——此时示例承载的通用能力已被使用方业务覆盖。**方式**：直接提交删除；本节的适用范围只有下列白名单，超出白名单的内容（尤其是使用方自己的业务）退役时仍走正常的 Change。

删除白名单：

- 整目录或整文件：`packages/sdk/src/example/`；`packages/protocol/testing/shadow/example/`；`packages/e2e/tests/example/`、`packages/e2e/tests/weapp/example/`；`packages/e2e/host/weapp/example-runner.ts`；`packages/e2e/tests/fixtures/` 下的 `SCN-TEMPLATE-EXAMPLE-*` 与 `FLOW-TEMPLATE-EXAMPLE-*`；`packages/e2e/tests/tooling/SCN-TEMPLATE-EXAMPLE-*`；`openspec/specs/template-example/`；示例删除验收自身的用例 `packages/e2e/tests/tooling/SCN-TEMPLATE-ENGINEERING-008.spec.ts` 与 Fixture `packages/e2e/tests/fixtures/SCN-TEMPLATE-ENGINEERING-008/`（这条保证只在示例存在时有意义，随示例一起删除）。
- 片段：全仓库所有成对标记之间的内容（连同标记本身），包括 [packages/sdk/src/index.ts](../packages/sdk/src/index.ts) 的示例导出、`consumed-operations.ts` 的示例条目及其单测中的示例断言、[packages/e2e/host/weapp/app.js](../packages/e2e/host/weapp/app.js)、`packages/e2e/host/weapp/setup.ts`、`packages/e2e/host/weapp/vite.config.ts` 与 [packages/e2e/src/drivers/weapp-host.test.ts](../packages/e2e/src/drivers/weapp-host.test.ts) 中注册与配置示例运行器的片段、本指南与各级 `AGENTS.md` 中指向示例文件或引用 `SCN-TEMPLATE-EXAMPLE-*` 的段落、包级 `AGENTS.md`「子模块」一节中列出的示例模块条目、会创建副本的用例排除列表（[packages/e2e/vitest.config.integration.ts](../packages/e2e/vitest.config.integration.ts)）与集成测试配置中包含 `example` 的 `include` 条目中指向示例文件或示例删除验收的部分。
- JSON 中的示例键：`SCN-PROTOCOL-CONTRACT-002/protocol-matrix.json` 中示例接口的键（`CreateTrade`、`QueryTrade`），删除后执行 `pnpm fixtures:refresh SCN-PROTOCOL-CONTRACT-002`。
- 同步：`manifest.quality.coverageExclusions` 中指向已删除文件的条目。

**片段标记**：共享文件中只属于示例的片段用成对注释包裹——代码文件写 `// template-example:begin` 与 `// template-example:end`，Markdown 写 `<!-- template-example:begin -->` 与 `<!-- template-example:end -->`。只有注释行里的标记才算标记：字符串字面量与 Spec 正文中出现的同名文字不参与裁剪，也不会被当成标记。架构检查会校验标记成对出现、不嵌套；共享文件中引用示例、但没有被标记包裹的内容会被视为门禁依赖示例，示例删除演练会把它暴露出来。

删除后先运行 `pnpm format`（片段删除会留下空行与折行差异），再把改动 `git add -A` 或提交：源码清单取自 `git ls-files -co --exclude-standard`，未跟踪的新文件会进入清单，而工作区里已删除但尚未暂存删除的文件会在读取前被剔除——不 add 或提交，删除就不会反映到源码摘要，门禁会读到过期结论。然后运行 `pnpm check:fast` 与场景门禁清单模式（`pnpm check:scenarios --inventory`）：清单模式不要求平台报告，所以 `requiredIn` 含平台项目的用例会报 `missing binding`，这类问题在副本里预期存在、不代表删除有问题；除此之外应全绿。本节的删除发生在初始化阶段、副本里没有 active Change 时按运行约定不带作用域（仍在交付 active Change 时按「从方案到验收」第 4 条带作用域）。完整验收（含平台报告）由复刻验收的示例删除演练承担。

## 归档已知限制

OpenSpec 归档在两种情况下会被拒绝，需要手工处理（以下行为在 `@fission-ai/openspec` 1.6.0 上实测）：

- **整份能力退役**：delta 用 `REMOVED Requirements` 删掉某个 Spec 的全部 Requirement 时，重建出的 Spec 没有任何 Requirement，归档会报 `Spec must have at least one requirement` 并中止（`Aborted. No files were changed.`），主 Spec 也不会被更新。手工步骤：删掉该 Change 的对应 delta 文件，直接在 Change 内删除主 Spec 的 Requirement 段落；整份 Spec 清空时连同 `openspec/specs/<spec>/spec.md` 一起删除，再运行 `openspec archive <change> -y`。归档后确认 `openspec/specs/` 已无该 Spec，且 `pnpm check:scenarios` 与 `pnpm check:fixtures` 没有指向已删能力的悬空引用。
- **保留 ID、只改 Scenario 标题**：`MODIFIED` 块里换了 Scenario 标题、主 Spec 还是旧标题时会被拒绝，报 `current spec contains scenario(s) not present in the modified block`。手工步骤：先在主 Spec 中把标题改成最终标题（这一步单独提交），再归档只包含其余修改的 delta。

这两条限制都来自 OpenSpec 自身的校验；升级 CLI 时先重跑上述两种情形，确认行为是否变化。

## 版本对齐

接入官方脚手架（例如 Vite、Vitest、ESLint 的初始化命令）时，按 peer 依赖与 `engines` 统一版本，不要按脚手架默认版本覆盖模板已有的约束；`typescript`、`@types/node` 与 `@fission-ai/openspec` 的版本在 Design 中固定，升级需要单独说明理由。模板版本过旧时可以升级，并在模板反馈日志中记录升级前后的差异与实际影响。

## 使用方约定

- 反馈日志只记录**实际遇到、并已核实**的问题；每条注明问题出在模板代码还是使用方项目代码，避免把使用方自己的选择记成模板缺陷。
- 修改行为或接口先维护 Spec/Design/Tasks；已评审输入发生语义变更后重新评审。
- 长期约定落在项目级载体（`AGENTS.md`、schema、清单、脚本、指南、[架构文档](architecture.md)）上，Change 文档不能是唯一出处。
- Claude Code 版本要求不低于 v2.1.277；根与各级 `CLAUDE.md` 的首个非空行固定为 `@AGENTS.md`，本地的 `CLAUDE.local.md` 同样必须以 `@AGENTS.md` 开头，配对由 `pnpm check:project-map` 核对。
- 遇到问题时先查官方文档与业界或社区的成熟方案，查不到再做实验，最后才考虑自研；自研通用能力要在 Design 中写明查过哪些方案、为何不采用。

## 复刻验收

能力扩展后用"复刻验收"证明改造有效：由没有上下文的执行者照指南真的做一遍。

- **隔离副本**：在待验收的提交上执行 `git archive` 导出到临时目录（改动尚未提交时，改用 `git ls-files -co --exclude-standard` 复制工作区），`git init` 后只做一次初始提交，再按锁文件安装依赖（`pnpm install --offline --frozen-lockfile`）。待验收的 Change 仍是 active 时，先模拟交付状态：在副本中归档该 Change、移除其余 active Change，再删除副本中该 Change 的归档目录与 `artifacts/`，避免演练执行者读到规划与已知答案。
- **执行者**：每个演练派发一个全新的、不带上下文的 Agent。提示词只包含副本路径、"先读根 `AGENTS.md` 与指南"、操作目标与规则；禁止读取 `openspec/changes/` 与 `artifacts/`。
- **验收命令**：按"从方案到验收"的运行约定，演练执行者自己的工作仍在 active Change 中时用 `pnpm verify --change <该 Change>`；只有副本中没有 active Change 时才不带作用域。
- **输入范围**：为目标项目选一个代表性子集，在演练说明中写明包含哪些 Scenario 与接口。
- **通过标准**：确定性门禁全部通过；演练执行者的猜测记录按"指南已覆盖但未读到"、"指南缺失需修订"、"合理的自主判断"三类判定；每个已纳入范围的历史问题都必须不再复现。
- **证据**：写入 Change 的 verify 记录，内容包括提示词、执行者、步骤摘要、改动文件、门禁结果与猜测记录的处理。
